# Data Model

CKM Data Readiness Infrastructure — Persistence and Schema Design

This document defines the data model for the CKM Data Readiness Infrastructure POC. It covers all four data tiers from raw input to use-case ready representations, the check result and patch record schemas, demo session management, and the strategy for OMOP CDM and FHIR R4 representations.

This document is the authoritative brief for the Neon database schema setup. All table names, field names, and relationships defined here should be implemented exactly in the persistence layer.

| Core constraint: Raw data is never modified. Every transformation, normalization, patch, and derived metric is stored as a new record that references the original. This enables complete audit trails, demo session resets, and regulatory compliance. |
|----|

## 1. Four-Tier Data Architecture

Data flows through four tiers. Each tier adds a layer of processing without modifying upstream records. The tiers are implemented as separate table groups in Neon.

| **TIER 1 — RAW INPUT Original ingested data exactly as received from the source. Never modified. Serves as the permanent audit anchor for all downstream processing. Corresponds to Dataset A/B/C CSV files.** |
|----|

| **TIER 2 — NORMALIZED Raw records with companion NR (normalized reference) fields added by the pipeline. Includes terminology mappings, timestamp standardization, and structural corrections. Generated by the pipeline; stored alongside raw records with source references. Still read-only once generated.** |
|----|

| **TIER 3 — CHECK RESULTS AND PATCHES Check engine outputs (one result record per check per patient) and AI-suggested or human-authored patch records. All patch records carry full provenance metadata. Human approval is required before a patch is applied. Raw data is never touched.** |
|----|

| **TIER 4 — USE-CASE READY Aggregated readiness scores per patient per use case, plus OMOP CDM and FHIR R4 representations for analytics and interoperability. Generated from Tier 3 outputs. Tier 4 stores readiness outputs for all evaluated patients — including blocked and partial states — so the UI can show the full remediation arc. OMOP and FHIR generation may be restricted to patients meeting minimum thresholds for the relevant downstream use case.** |
|----|

## 3. Tier 2 — Normalized Records

Normalization adds companion NR fields alongside each raw field. NR fields are not stored by overwriting the raw value — they are stored as new records in a single normalized_fields table that references the original Tier 1 record by primary key. This preserves the raw value for audit while making the normalized value available for downstream processing.

| Implementation pattern: All normalization outputs are stored in a single normalized_fields table. One row per field normalized, per source record. This is simpler to inspect, easier to reset, and consistent with the session-scoped cleanup model. Do not use separate normalized\_\[table\] tables or materialized views for the POC. |
|----|

### 3.1 NR Field Pattern

| **Field** | **Type** | **Null?** | **Description / Notes** | **Tier** |
|----|----|----|----|----|
| source_record_id | VARCHAR(32) / UUID | N | Foreign key to the Tier 1 record being normalized. | 2 |
| source_table | VARCHAR(32) | N | Name of the Tier 1 table (e.g., 'patients', 'encounters'). | 2 |
| field_name | VARCHAR(64) | N | Name of the raw field being normalized (e.g., 'birth_date', 'code'). | 2 |
| raw_value | TEXT | N | Original value from Tier 1. Copied for reference. | 2 |
| normalized_value | TEXT | Y | Normalized value. NULL if normalization failed or was not applicable. | 2 |
| normalization_type | VARCHAR(32) | N | Type of normalization applied: date_format, terminology_map, value_standard, etc. | 2 |
| normalization_status | VARCHAR(16) | N | 'success', 'failed', 'not_applicable'. | 2 |
| normalized_at | TIMESTAMPTZ | N | Timestamp of normalization. | 2 |
| applied_patch_id | UUID | Y | Foreign key → patch_records.patch_id. Populated when this normalized value was produced from an approved patch rather than an automated rule. | 2 |
| demo_session_id | UUID | N | Session reference. | 2 |

## 4. Tier 3a — Check Results

The check engine evaluates each variable against the check registry defined in the Technical Specification. Each check produces one result record per patient. Check results are the input to use-case fitness evaluation and the trigger for remediation work items.

| The agentic infrastructure never receives raw data — only check result records. Each check result is approximately 200 bytes. Token cost scales with the number of checks, not the number of raw records. |
|----|

## 9. Foreign Key Constraint Design

Foreign keys in this schema follow two complementary session-aware patterns. Every session-scoped table carries both where applicable:

(1) Direct session FK. Every table with a demo_session_id column carries a direct FK from that column to demo_sessions(session_id). This enforces session membership at the DB layer independent of entity relationships, supports CASCADE on session deletion, and allows session-level operations (reset, audit) to act on the session table directly. Every table in the schema from Tier 1 through Tier 4 follows this pattern. The Tier 3 runtime-output tables carry this as an explicitly named, redundant session FK independent of their composite entity FK: `fk_check_results_session`, `fk_remediation_work_items_session`, and — added in V010 — `fk_use_case_pathway_results_session`, each `ON DELETE CASCADE`. The redundancy is intentional: session deletion cascades even where the composite patient link is absent or denormalized.

(2) Composite entity FK. Tables that reference an entity in another table additionally carry a composite FK referencing both the entity ID and demo_session_id together, pointing at a corresponding composite UNIQUE on the parent table. This enforces that every record belongs to an entity within the same demo session. Example: encounters.fk_encounters_patient references (patient_id, demo_session_id) → patients(patient_id, demo_session_id). The V010 table use_case_pathway_results follows this pattern via fk_use_case_pathway_results_patient → patients(patient_id, demo_session_id).

Tier 1 raw tables (other than patients) carry composite entity FKs to patients via this pattern. Tier 3 and Tier 4 tables carry composite entity FKs to patients and, where applicable, to other entities. cgm_readings is the documented exception below: it carries only the direct session FK, with no composite entity FK to patients, by design.

> **Exception — cgm_readings has no FK constraint to patients.** This is intentional. Dataset B Bug 1 loads CGM records with UUID-format user_ids that do not match any patient_id in the patients table. A database FK would prevent these records from loading, eliminating the identity linkage failure scenario the demo is designed to demonstrate. Identity validation is handled by the check engine (device_patient_linkage check) at the application layer.

### 10.2 Session Reset Sequence

Delete in reverse dependency order to respect foreign key constraints.

```sql
-- IMPLEMENTATION NOTE: The "Clear Tier 4 — OMOP CDM" block below (device_exposure,
-- measurement, drug_exposure, condition_occurrence, visit_occurrence, person)
-- references tables from the planned OMOP strategy (§8.1) that are NOT in the current
-- 21-table schema. This sequence documents the target design; against the demo DB
-- as-is, only the fhir_bundles, use_case_readiness, Tier 3, Tier 2, and Tier 1 DELETEs
-- are runnable.

-- 1. Deactivate session
UPDATE demo_sessions SET is_active = FALSE WHERE session_id = :session_id;

-- 2. Clear Tier 4 — OMOP CDM (before use_case_readiness and fhir_bundles)
DELETE FROM device_exposure WHERE demo_session_id = :session_id;
DELETE FROM measurement WHERE demo_session_id = :session_id;
DELETE FROM drug_exposure WHERE demo_session_id = :session_id;
DELETE FROM condition_occurrence WHERE demo_session_id = :session_id;
DELETE FROM visit_occurrence WHERE demo_session_id = :session_id;
DELETE FROM person WHERE demo_session_id = :session_id;

-- 3. Clear Tier 4 — use-case ready and FHIR
DELETE FROM use_case_readiness WHERE demo_session_id = :session_id;
DELETE FROM fhir_bundles WHERE demo_session_id = :session_id;

-- 4. Clear Tier 3 — checks, patches, work items, pathway results
DELETE FROM use_case_pathway_results WHERE demo_session_id = :session_id;
DELETE FROM remediation_work_items WHERE demo_session_id = :session_id;
DELETE FROM patch_records WHERE demo_session_id = :session_id;
DELETE FROM variable_readiness_scores WHERE demo_session_id = :session_id;
DELETE FROM check_results WHERE demo_session_id = :session_id;

-- 5. Clear Tier 2 — normalized
DELETE FROM normalized_fields WHERE demo_session_id = :session_id;

-- 6. Clear Tier 1 — raw input (optional; CSV files remain as reload source)
DELETE FROM weight_readings WHERE demo_session_id = :session_id;
DELETE FROM bp_readings WHERE demo_session_id = :session_id;
DELETE FROM cgm_window_metadata WHERE demo_session_id = :session_id;
DELETE FROM cgm_readings WHERE demo_session_id = :session_id;
DELETE FROM observations WHERE demo_session_id = :session_id;
DELETE FROM medications WHERE demo_session_id = :session_id;
DELETE FROM conditions WHERE demo_session_id = :session_id;
DELETE FROM encounters WHERE demo_session_id = :session_id;
DELETE FROM providers WHERE demo_session_id = :session_id;
DELETE FROM patients WHERE demo_session_id = :session_id;
```

Note: config-tier tables `condition_modules` and `use_case_specifications` (added in V010) ARE live in the current schema but are deliberately excluded from the reset sequence — they are loaded at app startup and persist across sessions as governance artifacts. Separately, the OMOP `concept` table is part of the planned OMOP layer (§8.1) and is NOT present in the current 21-table schema; in the target design it holds vocabulary reference data loaded once at schema setup and is never session-scoped. The two are distinct: the config-tier tables are present-but-excluded, whereas `concept` is absent from the schema as-is.

## 11. Neon Implementation Notes

Database: Single Neon project, single database named 'ckm_readiness'. Schema 'public' for all tables.

UUID generation: Use gen_random_uuid() for all UUID primary keys. Enable the pgcrypto extension.

Indexing: Index all foreign keys and demo_session_id columns. Index check_results on (patient_id, check_name, demo_session_id). The use_case_readiness tuple (patient_id, use_case_name, demo_session_id) is the UNIQUE upsert arbiter uq_use_case_readiness_upsert (V014), not a plain index.

JSONB: fhir_bundles uses JSONB. Add a GIN index for full-text search across FHIR bundles if needed.

Row-level security: Not required for the POC. Add in production when multi-tenant access is needed.

Migrations: Use a migration tool (e.g., Flyway or Prisma Migrate) to version the schema.

Dataset loading order: patients → providers → encounters → conditions → medications → observations → cgm_readings → cgm_window_metadata → bp_readings → weight_readings. All within a single transaction per session.
